# Most Valuable Feedback submission draft

RewardSeal uses Nebius Token Factory to serve Nemotron as a coding-task attacker, Token Factory Sandboxes to execute task code, and Tavily for host-side search. Gates and hole labels are computed in code. Our most useful feedback comes from running this loop: cost reconciliation, isolation controls, and explicit outcomes for interrupted reasoning and tool use would make these services easier to operate and evaluate. These are observations from this project's recorded development and runs, rather than claims about the services today.

Token Factory's OpenAI-compatible API let us use a familiar client, but we could not find a hard spending limit per key or project, or an API for remaining trial or promotional credit. We checked the console between batches and built reservations, settlement from reported usage, caps and a halt into `rewardseal/budget.py`. Our ledger deliberately errs high and did not match console billing. A project-level hard limit plus a balance and usage endpoint would let an agent operator reconcile costs without manual console checks. Pricing was available through the verbose model listing rather than the default listing; documenting that path prominently, or including prices by default, would reduce hand-maintained configuration. We also need documented billing and retry semantics for timeouts and service errors. Our timeout and HTTP 503 outcomes remain inconclusive; they do not count as attacker failures. An idempotency mechanism and a request identifier linked to billing would help distinguish retriable transport failures from completed, billable inference.

Sandboxes enabled the task execution, but the API's non-zero cost estimate did not correspond to a Sandboxes billing line in our recorded console checks. We initially booked the estimate as spend, then separated it from the Token Factory counter. Please label estimated versus billed cost explicitly and provide a run listing with status, duration and billing attribution. Image loading also had a delayed failure: `images.use` returned a handle for an unimported tag, and execution later raised `NotFoundError`. An early validation error or a clear example distinguishing `images.use` from `images.oci` would have avoided that debugging cycle. For our untrusted attacker workload, the SDK lacked a per-session network-off option. We used guest-side `unshare -rn`, connection probes and pinned binary checks, with residual limits documented in ADR 0002. Platform-enforced network isolation per session or branch, and an optional host allowlist, would reduce this custom guard code. A consistent timeout result stating whether the guest process was terminated would also make interrupted runs easier to interpret.

Tavily worked as a host-side harness recon search on `schematics_to_swagger-7`; the attacker did not choose that search and made no search calls of its own in the committed certificates. The usage endpoint initially lagged our successful call and later caught up, so we could not immediately reconcile our counter with the provider's. A documented reporting delay and a request identifier or usage field in the search response would make that reconciliation clearer. The separate web-exposure audit is a dated findability check, including an oracle PR-URL query. Its null result does not establish absence of web exposure, and we do not claim Tavily changed an attacker outcome.

Nemotron Super handled the shell-tool attacker loop through Token Factory, but many recorded attempts ended at a step or token limit without submitting. Those outcomes are inconclusive, rather than evidence that the environment resists another attempt. A Nano smoke response with a small `max_tokens` returned `content: null`, `finish_reason: length`, and reasoning text without the requested answer; the reported usage did not split reasoning tokens (a smoke-test observation, not committed as a record). Please document a useful minimum output allowance, expose reasoning-token usage, and provide supported reasoning controls and examples for long tool-use loops. Consistent model-ID naming would also reduce configuration mistakes. Our Ultra experiment was limited to a single task, so we have little comparative feedback on it. The most valuable improvements for this project would be reconcilable billing, platform-enforced isolation, and clear reasoning/timeout outcomes: each would replace custom operational code with a service contract we can record and test.
